# 截图自动记账设计文档

> 项目暂名 ledger-snap。整理于 2026-10-21。状态：阶段 1 已实现，并提前做了转账、信用卡还款和结构化修改；用测试账号和 32 张合成截图跑通了端到端流程（第 9 节有测试结果）。快捷指令还没在真机上搭建，步骤见 [shortcut.md](shortcut.md)。

## 1. 目标与范围

在 iPhone 上轻点背面截图，服务端识别截图中的交易，自动写入钱迹，并在同一次运行里允许用一句话修改。

- **用户**：自己和几个朋友，不做大规模分发。
- **原则**：方便好用优先，隐私不是主要约束。截图整张上传，服务端保存钱迹密码 MD5 以便自动重新登录。
- **独立实现**：不依赖 LedgerLens 的 CLI 或代码，钱迹客户端在本项目内自行实现（第 6 节）。
- **不做**：
  - 快捷指令运行结束后的修改，这类修改直接去钱迹 App；
  - 借贷、分期、报销等特殊账单；
  - 多币种；
  - 本地识别方案。

## 2. 总体结构

```
iPhone 快捷指令
  │  截屏 → JPEG → HTTPS 上传
  ▼
服务端（Go，单个二进制）
  ├─ 火山引擎 OCR：识别文字行、位置、字号
  ├─ OpenRouter 决策接口：类型、金额、时间、分类、资产等判断
  ├─ OpenRouter 视觉 LLM：判断不准时兜底
  ├─ 记忆表：资产别名、商户规则
  └─ 钱迹客户端（本项目实现）：登录、签名、读目录、拉账单、写账单
        ▼
     钱迹 API
```

## 3. 快捷指令

### 触发

在「设置 › 辅助功能 › 触控 › 轻点背面」里，把“轻点两下”设为本快捷指令；iPhone 15 Pro 及以上也可以用操作按钮。「截屏」截的是当前屏幕，所以必须停在支付结果页时直接触发，不能从快捷指令 App 或小组件里点着运行。

### 首次运行

1. 读取 iCloud 快捷指令文件夹里的 Token 文件，不存在则继续下一步。
2. 「要求输入」钱迹账号和密码，用「生成哈希值」算出 MD5。
3. 调用 `POST /v1/login`，带上安装时填写的邀请码。
4. 把返回的服务端 Token 存成文件。

### 每次运行

1. 「截屏」→「转换图像」为 JPEG → `POST /v1/recognize`，同时上传截图和手机当前时间。
2. 按返回的 `status` 处理：

| status | 快捷指令的动作 |
| --- | --- |
| `written` | 已写入。弹「从菜单中选取」，标题为 `summary`，选项「好 / 修改 / 撤销」 |
| `needs_confirm` | 未写入，例如疑似重复。弹菜单，标题为 `reason`，选项「仍然记下 / 不记」 |
| `rejected` | 不记账。弹通知显示 `reason`，例如“不是交易页面”“交易未成功” |

3. **修改**：「要求输入」一句话（可用键盘语音），调用 `POST /v1/records/{id}/correct`，用新的 `summary` 再弹一次菜单，可以反复修改。
4. **撤销**：调用 `DELETE /v1/records/{id}`。
5. 任何接口返回 401：删除 Token 文件，下次运行重新登录。

### 分发

用 iCloud 链接分享，借助「导入问题」在安装时填写服务器地址和邀请码。识别逻辑全在服务端，服务端更新后，朋友不用重装快捷指令。

## 4. 服务端接口

所有接口（登录除外）都要带 `Authorization: Bearer <token>`。服务端只保存 Token 的哈希值。

| 接口 | 请求 | 作用 |
| --- | --- | --- |
| `POST /v1/login` | `{"account","password_md5","invite_code"}` | 校验邀请码，登录钱迹，拉取分类、资产和账单，返回 `{"token"}` |
| `POST /v1/recognize` | multipart：`image`、`client_time`（Unix 秒） | 识别、匹配、写入，返回识别结果 |
| `POST /v1/records/{id}/confirm` | 无 | 写入一条 `needs_confirm` 的记录 |
| `POST /v1/records/{id}/correct` | `{"text"}` | 按一句话修改已写入的账单 |
| `DELETE /v1/records/{id}` | 无 | 删除已写入的账单，或丢弃未写入的记录 |

识别结果：

```json
{
  "record_id": "r_01J...",
  "status": "written",
  "summary": "支出 25.00 · 三餐/午餐 · 招行信用卡 · 12:31",
  "reason": "",
  "uncertain": ["category"]
}
```

`uncertain` 列出置信度低的字段，`summary` 里会在这些字段旁加问号。

## 5. 识别流程

### 5.1 OCR

服务端用原图调用火山引擎 OCR，拿到每一行文字及其位置和框高。框高可以近似看作字号。

### 5.2 代码先处理

1. **金额候选**：从文字行里找出所有金额样式的数字（含 `¥`、`元`、正负号、千分位、两位小数），按框高从大到小排序。每个候选附带同一行或相邻行的关键词，例如“实付”“合计”“优惠”“余额”“原价”。
2. **时间候选**：找出所有日期时间字符串，统一解析为北京时间。缺年份时，用手机时间补全。
3. **文字行**：保留各行文本作为“哪一行是商户”的选项。
4. **查记忆表**：
   - 如果 OCR 文字里包含某条资产别名（例如“招商银行信用卡(1234)”），资产直接确定；
   - 商户在识别出商户行后再查，命中商户规则时分类直接确定。

### 5.3 决策模型

通过 OpenRouter 决策接口发**一次**请求。`state` 里放两样东西：缩到长边 1568 像素的截图（这是 Jev 的尺寸上限），以及 OCR 文字。所有问题在同一次请求里并行回答：

| 问题 | 类型 | 选项 |
| --- | --- | --- |
| 是不是一笔已成功的交易 | noul | — |
| 交易类型 | choice | 支出 / 收入 / 自己账户之间转账 / 信用卡还款 / 退款 / 不是交易 |
| 金额 | choice | 金额候选 + “没有” |
| 时间 | choice | 时间候选 + “截图里没有” |
| 支出分类 | choice | 支出分类列表 |
| 收入分类 | choice | 收入分类列表 |
| 资产 | choice | 资产列表 + “看不出来”（记忆表已确定时不问） |
| 转入资产 | choice | 资产列表（只在可能是转账时使用） |
| 商户 | choice | OCR 文字行 |

约定：

- 分类按类型分成两个问题同时问，根据“交易类型”的答案取其中一个。
- 选项顺序固定为钱迹目录里的顺序，保证同一张截图每次结果一致。
- 能用是非问题表达的判断，优先用 noul。
- Jev 的 choice 最多 255 个选项，分类超出时只保留叶子分类。
- 每个问题的原始概率都写进识别记录。

### 5.4 分流

1. 不是交易，或交易没成功：返回 `rejected`。
2. 类型为退款：阶段 1、2 返回 `rejected`，提示到钱迹里处理；阶段 3 改为关联原账单。
3. 没有金额候选，或者金额、类型的置信度低于阈值：交给视觉 LLM 兜底（5.5 节）。
4. 疑似重复：前后 5 分钟内已有同金额、同资产的账单，返回 `needs_confirm`。阶段 1 只和本服务写过的记录比对；阶段 2 有了本地账单缓存（6.4 节）后，也和在 App 里手动记的账单比对。
5. 有置信度低的字段时（`recognize.confirm_uncertain = true`，默认开启）：先不写入，返回 `needs_confirm`，说明哪几项拿不准；用户确认或修改后确认才入库。
6. 其他情况：写入，返回 `written`。

**时间规则**：截图里有交易时间就用截图时间，没有就用手机时间。截图时间比手机时间早 24 小时以上时（比如截的是历史账单详情），仍以截图时间为准，并把 `time` 放进 `uncertain`。

**阈值**：不能直接照搬模型给出的概率。有人测出 choice 的概率会过度集中到第一名，而且选项顺序一变概率就变。阈值要用标注过的截图逐字段标定。

### 5.5 视觉 LLM 兜底

把这些交给视觉 LLM：原图（按模型的尺寸要求缩放）、带位置的 OCR 文字行、分类和资产列表（含 ID）、手机时间。要求它按固定的 JSON Schema 输出，字段与决策模型的答案一一对应。推理档设为 low。

返回的分类 ID 和资产 ID 一律用目录校验，校验不过就当成没识别出来。

### 5.6 写入

所有写入都通过钱迹的 `bill/syncall` 接口完成（6.3 节）：

| 类型 | 钱迹账单 `type` | 关键字段 |
| --- | --- | --- |
| 支出 | 0 | `money`、`cateid`、`assetid`、`time`、`remark`，可带优惠 |
| 收入 | 1 | 同上，无优惠 |
| 自己账户之间转账 | 2 | `fromid`、`targetid`、`money`，可带手续费 |
| 信用卡还款 | 3 | 同上，`targetid` 为信用卡 |
| 退款（阶段 3） | 走 `bill/refund2` | 源账单 ID、金额、资产 |

备注写成商户名，便于日后按商户检索历史账单。

### 5.7 修改

把当前账单、分类和资产列表、用户那句话交给决策模型。分类、资产、类型各问一个 choice，每个都带“不改”选项。

- 如果这句话改的是金额或时间（“是 35 块”“昨天的”），交给 LLM 解析成修改项。
- 类型没变：用 `bill/syncall` 提交修改后的完整账单。
- 类型变了（如支出改转账）：在同一次 `bill/syncall` 里删除旧账单、新建新账单，记录指向新账单。
- 改了分类，就写一条商户规则；改了资产，就写一条资产别名。下次遇到同样的情况直接命中。

## 6. 钱迹客户端

本项目自己实现一个只覆盖所需接口的钱迹客户端，放在 `internal/qianji`，不引用、不调用 LedgerLens。

参考资料：

- 逆向接口文档：钱迹 Android 4.5.4 反编译整理，见用户本地的 `qianji-api-docs-apk454.zip`。建议解压到仓库 `docs/qianji-api/` 方便查阅。
- LedgerLens 源码（MIT 许可）：其中的签名、请求头和账单字段已经在线上验证过。只拿它对照实现细节，不作为依赖。

### 6.1 请求

- 地址 `https://api.qianjiapp.com/<ctrl>/<act>`，统一 POST，`application/x-www-form-urlencoded`。
- 服务端只支持 HTTP/1.1，而且**请求头名称必须小写**：`vs` 写成 `Vs` 会被当成旧客户端拒绝。Go 的 `Header.Set` 会把头名改成首字母大写，所以要直接写 `req.Header["vs"]`。
- 请求头：

| 头 | 值 |
| --- | --- |
| `ctrl`、`act` | 路径两段 |
| `os`、`osvs`、`pkg` | `1`、系统版本、`com.mutangtech.qianji` |
| `vs`、`vsn`、`mk` | 版本号、版本名、渠道。先沿用 LedgerLens 线上验证过的 `1207`、`4.5.1b3`、`beta` |
| `devbrand`、`devname`、`devid` | 设备信息；`devid` 每个用户随机生成一次后固定保存 |
| `clang`、`cregion`、`timezoneoffset` | `zh`、`CN`、`28800` |
| `reqidv2`、`tok` | 签名，见下文 |
| `utoken` | 登录后的 Token |
| `htoken` | 同步通道接口（`bill/syncall`、`syncv2/pull`）固定为 `1` |

- 登录后的每个请求，表单里都附加 `uid` 和 `fr`，值为钱迹用户 ID。
- 签名公式（`versionCode` 必须和 `vs` 一致）：

```
ms       = 当前毫秒时间戳（同一接口严格递增） + versionCode + 9081127
reqidv2  = md5("com.mutangtech.qianji" + ms + ctrl + act + "free20170908&x_*1127")
encreqid = md5(reqidv2 + "michaeljackson")
tok      = md5(reqidv2 + "1172020" + ctrl + encreqid + act)
```

- 响应统一为 `{"ec","em","data"}`：`ec == 200` 表示成功，`data` 是对象。
- 登录失效的判断：HTTP 401，或者 `ec` 不为 200 且 `em` 里含有 token、登录等字样。单纯的 HTTP 403 可能是签名或网关拒绝，不能当成登录失效。
- 账单、分类、资产等 ID 是 64 位整数，可能超出浮点精度：Go 里一律用 `json.Number`，对外以字符串传递。用户 ID 是不透明字符串。

### 6.2 用到的接口

| 阶段 | 接口 | 用途 |
| --- | --- | --- |
| 1 | `account/login` | `v` 为账号，`pwd` 为小写密码 MD5；返回 `data.user.id` 和 `data.token` |
| 1 | `category/listv2`、`asset/list`、`book/list` | 分类、资产、账本目录 |
| 1 | `bill/syncall` | 新增、修改、删除账单 |
| 2 | `syncv2/pull` | 增量拉取账单，用于去重和历史匹配 |
| 3 | `bill/refund2` | 退款并关联原账单 |

### 6.3 写账单

- 请求体：`v = {"bills":{"changelist":[账单...],"dellist":[ID...]}}`。
- 响应在 `data.sync_result.bill` 里：`new_ids`、`update_ids`、`del_ids`、`conf_ids`（冲突），以及 `has_failed`（可能是布尔值，也可能是 0 或 1）。
- 新增账单的 ID 由客户端生成：`毫秒时间戳 × 1000000 + 100000 + [0, 100000) 的随机数`。
- 新增账单的必备字段：

| 字段 | 值 |
| --- | --- |
| `id` | 客户端生成的 ID |
| `userid` | 钱迹用户 ID |
| `bookid` | 账本 ID，默认账本为 `-1` |
| `type` | 账单类型 |
| `money` | 金额 |
| `time`、`createtime`、`updatetime` | 时间，Unix 秒 |
| `remark` | 备注 |
| `status` | 固定为 `2` |
| `cateid` | 分类 ID |
| `assetid` | 资产 ID |
| `fromid`、`targetid` | 转出、转入资产 ID |
| `platform` | 固定为 `0` |
| `images` | `[]` |

  没用到的 ID 字段一律填 `-1`：普通收支的 `fromid`、`targetid`，转账和还款的 `cateid`，未关联资产时的 `assetid`。漏掉这些字段，钱迹会拒绝写入，LedgerLens 修过同样的问题。
- 优惠、手续费、统计开关都放在账单的 `extra` 里，格式参照 LedgerLens 的 `bill_write.go`、`transfer.go`。
- 修改：提交完整账单，`updatetime` 改为当前时间，`status` 仍为 `2`。删除：把 ID 放进 `dellist`。
- 写入结果以响应为准：ID 出现在 `new_ids`、`update_ids` 或 `del_ids` 里，而且 `has_failed` 为假，才算成功；出现在 `conf_ids` 里算冲突。
- 请求发出后才发生网络错误时，写入结果未知。2026-10-21 用测试账号实测：同一 ID 重发会出现在 `update_ids` 里，不会多出一笔。所以每条识别记录固定一个账单 ID，网络错误时用同一 ID 重发一次。

### 6.4 账单缓存（阶段 2）

用 `syncv2/pull` 增量同步账单到本地，作为去重和“同商户历史分类”的依据：

- 按 `bookid`、`pageoffset`、`pagesign` 翻页，直到 `has_more` 为假；翻页过程中 `bookid` 可能变化，要用响应给出的下一页参数。`lasttimes` 作为增量同步点保存，下一轮从它开始。
- 一轮翻完才提交本轮的新增、更新、删除和最终同步点，中途失败就保留旧缓存。
- 这些分页细节，以逆向文档和 LedgerLens 的实现为准。

### 6.5 登录与重试

- **登录**：每个用户保存账号、密码 MD5、钱迹用户 ID、Token 和 `devid`。
- **读请求**：遇到登录失效，自动用保存的 MD5 重新登录一次，再重试。
- **写请求**：钱迹明确返回登录失效时，说明这次写入没有被接受，可以重新登录后重发；网络错误按 6.3 节的“结果未知”处理。
- **登录被拒**：返回 401，让快捷指令重新输入账号密码，不要用同一凭据反复重试。
- **串行**：同一用户的钱迹请求在服务端串行执行。

### 6.6 维护

钱迹协议现在由两个项目各维护一份。钱迹升级、签名或版本号失效时，本项目要单独更新。升级 `vs` 等版本参数之前，先用测试账号跑一遍登录、读目录、写入、删除的冒烟测试。

## 7. 数据存储

```
data/
  app.sqlite                 用户、钱迹会话、目录缓存、账单缓存、识别记录、记忆表、邀请码
  images/<uid>/<record>.jpg  截图，保留 30 天
```

| 表 | 字段 |
| --- | --- |
| `users` | uid、钱迹账号、密码 MD5、钱迹用户 ID、钱迹 Token、devid、服务端 Token 哈希、使用的邀请码、创建时间 |
| `invite_codes` | 邀请码、剩余次数 |
| `catalog` | uid、种类（分类、资产、账本）、原始 JSON、刷新时间 |
| `bills`（阶段 2） | uid、账单 ID、原始 JSON、发生时间、金额、资产、备注；以及每个账本的同步点 |
| `records` | id、uid、时间、status、截图路径、OCR 结果、决策模型原始输出、兜底输出、最终字段、写入的账单 ID 与原始 JSON、各环节耗时 |
| `asset_aliases` | uid、支付方式原文、资产 ID、命中次数、更新时间 |
| `merchant_rules` | uid、商户、分类 ID、命中次数、更新时间 |

- 密码 MD5 和钱迹 Token 等同于登录凭据。数据库文件权限设为 0600；如果想再加一层，可以用服务端主密钥加密这两列。
- 目录在登录时拉取一次；识别时如果发现距离上次刷新超过一定时长，就在后台刷新。
- 识别记录完整保存模型的输入和输出，以后调整提示词或阈值时可以回放对比。

## 8. 外部服务与配置

| 服务 | 用途 | 备注 |
| --- | --- | --- |
| 钱迹 API | 登录、目录、账单读写 | 非官方协议，见第 6 节 |
| OpenRouter 决策接口 `POST /api/alpha/decisions` | 决策模型 | alpha 版，格式可能变，必须放在适配层后面 |
| OpenRouter 对话接口 | 兜底视觉 LLM、修改语句解析 | 要求 JSON Schema 输出 |
| 火山引擎多语种 OCR（`MultiLanguageOCR`，`2022-08-31`） | 文字识别，默认 | 图片每边不超过 2048 像素，服务端先缩小再把坐标换算回原图。第三方页面写的价格是 0.015 元/次，新账号送 5000 次，以官网为准。当前密钥没有通用文字识别 `OCRNormal` 的权限 |
| 谷歌 Cloud Vision（`DOCUMENT_TEXT_DETECTION`） | 文字识别，备选 | 按符号的换行标记拼出文字行 |
| 百度 OCR（高精度含位置版） | 文字识别，备选 | 会返回全角冒号等字符，识别前统一转成半角 |

配置统一用环境变量：`OPENROUTER_API_KEY`、`VOLC_ACCESS_KEY`、`VOLC_SECRET_KEY`、`DECISION_MODEL`、`FALLBACK_MODEL`、`INVITE_CODES`、`DATA_DIR`，以及可选的 `DATA_KEY`（用于加密凭据列）。

**部署地区**：OpenRouter 上的 OpenAI、Anthropic 模型拒绝来自中国大陆和香港的请求，所以服务器要放在日本、新加坡或美国。火山 OCR 在国内，钱迹的接口大概率也在国内，海外服务器调用它们会多几十到一百多毫秒。容器只提供 HTTP，HTTPS 由外部的反向代理负责。

## 9. 模型选型与评测

### 决策模型候选

## 11. 风险

- **钱迹协议**：用的是非官方协议，请求头里的版本号是写死的，钱迹升级后可能失效；这份协议实现还要在两个项目里各维护一份。服务器 IP 登录会不会触发风控、会不会挤掉手机上的登录，都还没实测。
- **决策模型**：OpenRouter 决策接口是 alpha 版；Jev 的图片输入是实验功能；choice 的置信度不可靠。
- **托管凭据**：服务端保存朋友的密码 MD5 和钱迹 Token，使用前要告诉朋友。
- **地区限制**：服务器不能放在中国大陆或香港。
- **识别出错**：每次都弹菜单，可以当场修改；运行结束后的修改去钱迹 App。
